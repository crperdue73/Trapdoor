Host `test-trapdoor` (`192.168.111.45`), 2026-11-06, as root. This closes the
execution half of G1. The results are partly good and partly a new, larger
problem. Both are reported here with the commands that produced them.

Evidence: `out/g1/` on the host — backup, `apply-run1.log`, `apply-run2.log`,
`chain-after-run{1,2}.txt`.

## The instruction did its job

Before running `--apply`, the dry run's report was read rather than skimmed.
It was wrong, twice, and the fix found a third defect:

1. `CIDR_NOTE` for the /16 case contained literal newlines followed by `#   `,
   so the report it printed was split by spurious comment markers.
2. The iptables example in the report carried doubled backslashes and an
   angle-bracket placeholder. The report block lives inside an **unquoted
   heredoc**, so bash executed them: a command-substitution syntax error went
   to stderr and the printed rule line came out with its source match deleted.
3. The paragraph I wrote to document (2) contained backticks, which the
   unquoted heredoc also executed, and a `${...}` which under `set -u` killed
   the report outright.

Each fix caused the next defect. The lesson is not "escape more": it is that
**comment text inside an unquoted heredoc is still shell syntax.**

## The new problem: DOCKER-USER is not in the path on this host

This is the finding that matters. `firewall.sh` and `verify.sh` both assert
that a rule in `DOCKER-USER` restricts the decoy. On `.45` it does not.

Measured:

- `iptables -L DOCKER-USER -v -n` after a remote request from `.43`: the
  catch-all `RETURN` gains 12 pkts / 2230 bytes; the `DROP` rule above it
  stays at **0 pkts**.
- A test rule `DROP tcp dport 8080` with **no source match** was inserted at
  position 1. A local request to `http://192.168.111.45:8080/` still returned
  **200**, and the rule counted 0 packets.
- `ss -tlnp` shows `LISTEN 192.168.111.45:8080 users:(("docker-proxy",...))`.

Conclusion: traffic to the published port is served by `docker-proxy` over
**loopback**, not DNATed through `FORWARD`. `FORWARD → DOCKER-USER` is never
reached, so no rule there can allow or deny it.

This contradicts `scripts/firewall.sh`'s header comment, which states the
measured path as `nat PREROUTING → DOCKER → DNAT → FORWARD → DOCKER-USER` and
notes "12 pkts / 2230 bytes" as proof that DOCKER-USER sees off-box traffic.
Those 12 packets are real — they are Docker's own traffic, not the decoy's.
The counter was read as evidence that the hook was in the path, when it only
showed that the chain was referenced.

**Consequence: the `--apply` block is a correct rule written to a chain that
the decoy's traffic never visits.** It applies cleanly, verifies cleanly,
is idempotent, and enforces nothing. That is the same failure shape as the
near-vacuous `! -s 192.168.0.0/16` rule already documented in D3 — a control
that looks real because everything around it is green.

## What still has never been shown

**No rule in `DOCKER-USER` has ever been observed to deny a packet on this
host.** Until a DROP in the actual path flips a 200 to a timeout, D1–D4 and
the `--apply` block describe a firewall that has never refused anything.

## To close it

1. Determine the real path on `.45`: is `docker-proxy` (userland proxy)
   enabled? `network_mode` / `userland-proxy` in Docker's daemon config.
   With userland-proxy disabled, publish goes through iptables DNAT and
   `DOCKER-USER` becomes reachable.
2. Whichever path is real, write the rule to **that** path and prove it with
   the negative test used here: insert DROP, make one request from a remote
   host, require a timeout rather than 200.
3. Add the negative test to `scripts/verify.sh` as its own check, so the
   containment claim cannot pass without a rule having refused something.
   A firewall check that cannot fail is not a check.
